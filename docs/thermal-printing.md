# Thermal labels and customer invoice PDFs

The Exeo 9250 label preset starts at 50 × 25 mm with a 1.5 mm safe edge margin and a 203 dpi layout assumption. Measure the loaded stock and confirm the printer driver resolution before use. The backing gap is handled by the printer driver; it is not printable label area. Print the PDF at 100% / actual size with matching custom paper, no browser headers and no fit-to-page scaling. Verify a physical sample and scan its QR before printing a batch.

New label configurations start with item name, SKU, weight, price and product QR. Existing saved configurations remain available. Preview and PDF use the same measured layout. Every item in a batch is checked. Auto-fit reduces text first, never below 6 pt. Product QRs retain four quiet modules and at least 12 mm or two printer dots per module, whichever is larger. Unresolved overflow blocks PDF generation, including after the server returns the final item data. Selected barcodes are anchored inside a reserved footer and retained by removal suggestions. Optional branding, location, dimensions and other details can be removed explicitly. Long essential content may require taller stock or shorter saved text.

Code 128 barcodes encode the full SKU. They use two printer dots per module where stock width permits, otherwise one whole dot per module with a visible density warning. Preview and PDF use identical bar widths and ten-module quiet zones. A dense barcode is not guaranteed to work with every physical scanner; test the printed result and use wider stock if necessary. Text resizing cannot shorten the encoded SKU. The regression screenshot SKU has been software-decoded from a 203 dpi PDF raster alongside its product QR.

Label content has a stable order regardless of selection order. An internal name prints when a saved value exists; missing names are identified beside the checkbox and in preview warnings. The print queue is a centered searchable modal with batch selection. Preview zoom changes screen magnification only, never PDF dimensions. Fitting messages and dimensions have separate layout space.

The fitter tests normal and compact layouts at descending 0.5 pt steps and displays the applied font size beside the requested size. Short gem type, colour and shape values share a row when needed; every selected value is retained. Item headings shrink to the base size below 7 pt. Logo and barcode share a reserved footer row with separate horizontal space. Text that cannot fit is moved into an explicit overflow list below the preview and cannot be printed; it is never drawn through a code or graphic. Pairwise geometry tests cover 256 combinations of text and footer fields, including both reported screenshot selections. The fuller screenshot selection fits at 6.5 pt with a 12 mm QR on 50 × 25 mm stock.

The inventory workspace includes gemstone/location filters, search across SKU and internal names, sortable products and weights, row previews, SKU copying, select-all-results, selected-only view and page-size controls. Selection persists across pages and filters. Queuing selected items refreshes the cart badge.

Queued items are removed only after successful PDF generation and job completion. The preview opens its output window before asynchronous server work to avoid popup blocking, with a download fallback. Reprint mapping uses the stored internal name or falls back to the inventory name for older jobs.

Set `ERP_PUBLIC_URL` in the deployed environment to the public HTTPS origin serving this ERP, such as `https://erp.example.com`. This must host `/api/public/invoice/[token]/pdf`; a storefront without this ERP route cannot serve invoices. Receipt generation uses that explicit override or the browser's actual ERP origin; it does not assume `APP_BASE_URL` is the ERP because it may describe the storefront. Other server invoice links can fall back to `APP_BASE_URL` or `NEXTAUTH_URL`. Invalid/local addresses result in a visible warning and an omitted QR; the rest of the receipt remains printable.

The download endpoint resolves an active invoice by its unguessable token and generates an attachment using the canonical invoice PDF renderer, including that invoice's saved display options. It requires no customer login, does not write payments, and disables caching and indexing. Anyone holding the link can download the invoice; disabling the invoice or rotating its token invalidates it.

Thermal invoices use the canonical invoice data builder rather than a separate tax calculation. Existing invoice type, export conversion rate, certificate details, SKU visibility, totals, discount, charges, payment ledger, customer GSTIN and approved terms drive the renderer. No tax rate, origin/treatment claim or export exemption wording is invented. Foreign currency rendering requires the saved conversion rate. The detailed profile includes amount in words for INR/USD/EUR; other supported currencies retain their numeric totals without invented currency names. Unsupported font characters fail visibly and direct the operator to the standard PDF.

The invoice studio supports compact/detailed profiles and 50/80/100 mm widths, an optional monochrome logo, certification details, financial summary, secure download QR, PDF preview, download and browser printing. Receipts grow from measured content. Receipt QRs retain four quiet modules and at least three printer dots per module. Receipts over 1400 mm direct the user to the standard multipage PDF. Width choices do not imply the connected printer supports each width. Use continuous stock; a long invoice cannot fit on a single die-cut product label.

Before output, the server validates the preview hash and saves the invoice data in existing `InvoiceVersion` history with reason `Issued thermal document snapshot (v1)`. Reprints of that invoice revision use the saved data; later inventory/customer/company-setting changes do not rewrite it. The customer PDF download uses the same saved data when an issued snapshot exists for the invoice's current `updatedAt` revision. An explicit invoice update creates a new revision while the previous snapshot remains in history. This preserves rendered billing data, not immutable PDF bytes; remote logo assets and renderer changes can affect presentation. Before first issuance, previews use current data. No database migration or new invoice number is needed. Print/open/download requests are logged; this records a request, not confirmation that the physical printer completed it.

Already printed QR codes retain their old target. Reprint affected receipts after deployment. A QR printed with only a storefront URL cannot identify an invoice and cannot be recovered automatically.

Checks: `npm run test:thermal` and `npx tsc --noEmit`. The thermal suite covers fitting, internal-name visibility, screenshot barcode bounds, QR floors, receipt length, long addresses, export conversion, output headers and immutable snapshot reuse. UI verification uses synthetic fixtures and mocked server actions; real printer/driver and deployed ERP checks remain necessary.
