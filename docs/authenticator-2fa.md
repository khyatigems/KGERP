# Personal authenticator verification

Open **Security & 2FA** from the user menu, or **Settings → Security & 2FA**.
Every signed-in user can manage their own authenticator. Company email policy
and its shared mailbox remain restricted to users with `settings:manage`.

## Enrollment and sign-in

- Enter the current ERP password, scan the QR in a compatible TOTP app, and
  enter a current app code to activate. A manual setup key is also available.
- In Microsoft Authenticator, use **+ → Other account (Google, Facebook, etc.)**.
  Use **Enlarge QR code** if the camera has difficulty focusing. If setup is
  open on the same phone, use **Enter code manually**, the displayed account
  name and setup key. Restarting setup replaces the previous QR and key.
- When company email verification is enabled, activation also requires the
  browser-bound code sent to that mailbox. Issuing a QR alone does not enable MFA.
- Save the eight personal recovery codes displayed after activation. They are
  shown once, are bound to the account and enrollment, and each works once.
- Enrolled users default to password plus authenticator. Starting this flow does
  not send an email OTP. The company email method is an explicit fallback when
  its policy is enabled. Existing completed-login alerts still follow that policy.
- Users without an app continue to use the existing company email policy.
  A personal authenticator remains required even if company email 2FA is disabled.
- Remove an app with the current password and a fresh app code or unused personal
  recovery code. Removal invalidates its secret and recovery codes. Setting up
  again issues a new secret and recovery set.
- Enabling/removing a personal app invalidates that account's older sessions.
  Save recovery codes before selecting **Sign in again**. Other users' sessions,
  authenticators and company email policy are unchanged.

## Deployment

The existing `ERP_SECRET_ENCRYPTION_KEY` must be configured and stable before
enrollment. Reuse the application's existing key; changing it also affects other
encrypted credentials. TOTP secrets use the existing AES-256-GCM secret store,
with the user ID inside the encrypted payload. Recovery codes use keyed hashes
with `AUTH_SECRET` (or `NEXTAUTH_SECRET`). Back up keys with the database.

Two additive tables, `SecurityAuthenticator` and `SecurityAuthenticatorRecovery`,
are initialized through the existing runtime-schema pattern. No existing data
or company policy is migrated. No user is enrolled automatically.

TOTP follows RFC 6238 using SHA-1, six digits and 30-second steps. Verification
accepts the current step and one adjacent step for clock drift. An atomic update
prevents accepting the same or an older step twice, including parallel requests.
Login uses the existing durable account/IP budgets; enrollment and removal have
additional per-account limits. QR images are generated on the application server.
Do not send enrollment keys to external QR services or include them in logs.

## Verification

`npm run test:security` covers RFC vectors, account isolation, encrypted storage,
enrollment proof, concurrent replay, direct credential enforcement, email fallback,
personal recovery, session revocation, the existing email flow, and responsive UI.
Tests use temporary databases and synthetic mail/UI providers; they do not send
real email. Email layouts are rendered at 320, 390, 640, 1440 and 1920 pixels.

The authenticator suite also runs against the deployed libSQL adapter using a
temporary local database. With the pinned adapter version, raw BIGINT reads must
select decimal text and normalize it explicitly; a plain `SELECT *` fails when
reading the setup expiry and replay counter. This test covers activation, expiry,
app verification, replay rejection, recovery and removal. Server failures expose
a support reference and log only operation/error codes, without setup secrets.

QR regression checks independently decode the generated image and browser-rendered
normal, dark and enlarged views at 320, 390 and 1440 pixels. QR images have an
opaque white four-module quiet zone, integer pixel scaling at source and a square
responsive display. These checks do not replace testing a physical phone camera.

Gmail's native copy-code card is generated by Gmail. The Razorpay sample has a
normal HTML code and no custom copy action or special OTP schema. Our code remains
contiguous selectable text with an OTP subject/label. Rendering tests cannot
confirm Gmail's live classification; check a delivered message after deployment.
